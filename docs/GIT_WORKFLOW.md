# Регламент работы с Git (GIT_WORKFLOW.md)

Настоящий документ регламентирует порядок взаимодействия с Git-репозиторием https://github.com/9379998-creator/ege-matematika-11.git для всех ИИ-агентов и разработчиков.

---

## 1. Подготовка перед началом работы

Перед внесением любых изменений выполните обязательную диагностику:
1. **Проверка корня**: Убедитесь, что рабочая директория — G:\Общие диски\026-Фото_Школа_ОГЭ\ЕГЭ\Учебные_материалы (в ней находится файл .git).
2. **Проверка origin**: Выполните git remote -v. Единственный допустимый адрес: https://github.com/9379998-creator/ege-matematika-11.git.
3. **Проверка статуса**: Выполните git status. Рабочее дерево должно быть чистым, либо незакоммиченные файлы должны быть осознанно проверены. Чужие правки затирать категорически запрещено.
4. **Проверка обновлений**: Выполните git fetch origin для получения актуального состояния удалённого репозитория.

---

## 2. Изоляция изменений в тематических ветках

- Прямая работа и коммиты в ветку main **строго запрещены**.
- Любая новая задача выполняется в отдельной ветке, созданной от актуальной origin/main:
  `ash
  git checkout -b agent/<краткая-тема>
  `
  *(Пример: gent/numbers-fractions, gent/probability-bayes)*.

---

## 3. Подготовка и проверка перед коммитом

Перед фиксацией изменений агент обязан:
1. **Проверить математику**: Все расчёты, формулы, округления и таблицы перепроверяются.
2. **Проверить разметку**: Синтаксис Markdown, KaTeX-формулы ($...$, $$...), таблицы и относительные ссылки на разделы.
3. **Проверить diff**: Выполнить git diff и внимательно изучить все вносимые изменения.
4. **Точечный staging**: Добавлять в индекс только файлы своей задачи:
   `ash
   git add path/to/specific-file.md
   `
   **Категорически запрещено** использовать команду git add . без разбора.
5. **Фильтрация секретов и PII**: Убедиться, что в коммит не попадают персональные данные учеников, пароли, токены, ключи API, временные файлы и файлы из архива ОГЭ старое.

---

## 4. Разделение коммита и push. Запрос подтверждения

> [!IMPORTANT]
> **Коммит и push — это два принципиально разных действия.**  
> Создание коммита фиксирует изменения в локальной истории. Push отправляет их в публичный репозиторий GitHub.

**До выполнения коммита и отправки (push)** агент обязан:
1. Сформировать понятную сводку для пользователя:
   - Список подготовленных файлов;
   - Краткий смысл изменений;
   - Имя целевой ветки.
2. Запросить у пользователя подтверждение на коммит и отправку.

---

## 5. Выполнение коммита и публикация

После получения подтверждения пользователя:
1. Создать осмысленный коммит на русском языке с описанием сути:
   `ash
   git commit -m "Добавить методическое пособие по вычислению дробей в тему 01-numbers"
   `
2. Отправить на GitHub **только согласованную ветку**:
   `ash
   git push origin agent/<краткая-тема>
   `
3. Предложить пользователю открыть Pull Request в ветку main.
4. **Запреты**:
   - Запрещено выполнять автоматическое слияние (merge) PR в main без решения пользователя.
   - Запрещено использовать принудительную отправку (git push --force / git push -f).

---

## 6. Обработка нештатных ситуаций

1. **Сбой при push**: Если команда git push завершилась ошибкой (сеть, права, конфликт), агент обязан честно вывести сообщение об ошибке пользователю. Категорически запрещено писать «сохранено на GitHub», если команда завершилась с ошибкой.
2. **Обновления на GitHub**: Если удалённый репозиторий изменился, агент сначала проверяет чистоту локального рабочего дерева (git status), делает stash или коммит локальной ветки, и только затем подтягивает изменения (git pull / rebase), гарантируя сохранность локального труда.
